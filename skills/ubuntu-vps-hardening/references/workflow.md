# Ubuntu 24.04 audit and change workflow

## Collect evidence within the task scope

- Record the checked time, inputs, privilege level, source and vantage point for each finding. Mark unavailable, ambiguous or untested evidence unknown. Report the expected control, observed behavior, impact and proposed action. Review with the normal worker where possible and use a specifically granted privileged worker when needed.
- Confirm release, package origins, pending security updates, apt timers, unattended upgrade policy, exclusions, logs and reboot status. Check effective needrestart policy and affected units. Security upgrades can restart services during package transactions. Coordinate maintenance with active tasks and verify services and worker jobs afterward. [Ubuntu automatic updates](https://ubuntu.com/server/docs/how-to/software/automatic-updates/)
- Review management accounts, groups, effective sudo rules, authorized key fingerprints and file/directory ownership and modes. Keep key material and secrets out of output. Review sshd Include order, first-value precedence for applicable directives, and Match contexts. Use sshd -t and sshd -T with representative -C account/address contexts before reload and check the effective running socket and service. Check PasswordAuthentication, keyboard-interactive/PAM, AuthenticationMethods and PermitRootLogin as distinct controls. [Ubuntu OpenSSH](https://ubuntu.com/server/docs/how-to/security/openssh-server/), [Ubuntu Noble sshd](https://manpages.ubuntu.com/manpages/noble/en/man8/sshd.8.html)
- Inspect listening addresses, TCP/UDP services and relevant Unix sockets. Check ssh.socket, ssh.service, drop-ins and generated settings. A socket-activated listener can differ from the intended daemon settings and a daemon reload alone may leave the listener unchanged. [Ubuntu socket activation guidance](https://discourse.ubuntu.com/t/sshd-now-uses-socket-based-activation-ubuntu-22-10-and-later/30189)
- Trace IPv4 and IPv6 from approved client vantage points through provider firewall/routing, host interfaces, actual filter and forwarding rules, UFW and the listening process. Include VPN paths, ingress and necessary egress. UFW dry-run previews rule changes. Confirm permitted and denied reachability separately with scoped tests. [Ubuntu firewall](https://ubuntu.com/server/docs/how-to/security/firewalls/)
- Verify Tailscale identity, grants, routes and actual SSH path. Determine whether the tailnet carries ordinary OpenSSH or terminates Tailscale SSH under its own authentication and policy. An active VPN conveys connectivity evidence only. Verify independent provider console recovery separately. [Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)
- Check AppArmor enforcement and relevant denials for the affected processes. Review public service exposure, secret-file metadata (owner, mode, ACLs and traversal, without reading values), journal and app log retention, disk/inode and resource trends, backup coverage and last verified restore. Confirm provider console/account recovery and restoration options. [Ubuntu AppArmor](https://ubuntu.com/server/docs/how-to/security/apparmor/)

## Preserve management and service paths

Re-verify supplied topology. The anticipated baseline is a normal-user operator/controller and default worker as systemd services, a separately launched named root worker, host Caddy HTTPS for swarm.karstenjakobsen.dk proxying loopback 3001, Caddy admin on loopback 2019, SSH on 22, Tailscale and active UFW permitting 22/80/443. Preserve public 80/443 and ACME renewal, private internal ports, worker Unix sockets, provider/account authentication, SSH/Tailscale access and necessary egress. Prompt policy and a named root worker do not provide OS isolation.

- Root SSH disablement requires a fresh independent key login to an alternate administrator, sudo verified from that login, verified provider console recovery, and a retained working management session.
- Password SSH disablement requires tested key-based logins for each affected management account, including root if it remains a management account. Test new connections without cached sessions or password fallback. Root-login policy is a separate decision.
- SSH listener/firewall restrictions require observed effective listeners and an independently tested replacement path for each affected IP family, with recoverable rollback. Establish and test the replacement before removing the current path.

## Plan, execute and verify

Record the exact targets, minimal diff, dependencies, blast radius, health checks and rollback trigger. Preserve known-good configuration securely and have an executable restoration route before access changes. Keep the existing working session through fresh client checks. Avoid broad scripts, CIS presets, blanket sysctl, permission, service-disable or systemd sandbox changes, and unused platform installations. Route operator source, build, dependencies, .env, startup or update issues to external owner maintenance. Use ubuntu-fail2ban for authorized ban work.

Stage one recoverable change at a time. Validate relevant config and reload only the correct authorized component. Verify actual listeners, allowed and denied access from relevant paths and families, Caddy public HTTPS and renewal prerequisites, internal/private boundaries, necessary egress, service health and worker continuity. On failed checks, restore the prior state through the retained path or verified recovery path, then repeat checks. Report evidence for each applied, reverted or unresolved item.
